## 4. SINGLE STOCK INPUT ARCHITECTURE

Create one authoritative stock universe.

Use the existing stock input file wherever possible.

All three screeners and every future analytical module must consume the same stock universe.

Requirements:

- One source of truth.
- No independent stock lists inside individual screeners.
- No duplicate stock-list retrieval.
- Consistent ticker normalisation.
- Preserve original stock identifiers.
- Validate missing or invalid tickers.
- Provide a central stock-universe service.

If the stock list is updated, all modules must automatically use the updated version.

Do not introduce another stock input file without a documented technical necessity.

## 5. CENTRAL DATA ACQUISITION ENGINE

This is one of the most important architectural requirements.

Build a shared Data Acquisition Manager.

All screeners must obtain data through this manager.

Centralise:

- Historical OHLCV data.
- Latest market prices.
- Fundamental information.
- Benchmark information.
- Other existing external data sources.

Implement:

1. Central download manager.
2. Shared cache manager.
3. Download deduplication.
4. Cache freshness validation.
5. Incremental data updates where supported.
6. Request throttling.
7. Retry and timeout management.
8. Download audit logs.
9. Data-source error handling.

Use a unique cache key based on:

Ticker + Data Type + Source + Period + Relevant Data Version.

When Screener 1 downloads a stock's OHLCV data, Screener 2 and Screener 3 must reuse the same cached dataset whenever it satisfies their data requirements.

Do not download the same information again merely because another screener is running.

If a screener needs a longer historical period or additional data fields, retrieve only the missing information.

Never return stale or incomplete data silently.

Maintain a clear distinction between:

- Raw source data.
- Shared normalised data.
- Screener-specific calculated indicators.
- Final analytical results.

Shared raw data must not be modified by individual screeners.

## 8. ANNUAL REPORT AI ANALYSIS ENGINE

Preserve the existing annual report analytical methodology.

Implement a controlled, resumable batch-processing framework.

MANDATORY REQUIREMENTS:

- Read the same central stock universe.
- Identify eligible annual reports.
- Process a maximum of 100 stocks per scheduled daily batch.
- Maintain a persistent processing queue.
- Prevent duplicate processing of the same report version.
- Save every completed analysis.
- Save pending and failed stocks.
- Automatically resume on the next scheduled day.
- Never restart completed work unnecessarily.


The system must stop processing Annual report  when either the 100-stock batch limit or configured token budget is reached.

Do not assume that 100 reports will always fit within a particular token allowance.

Use document extraction and section-level analysis wherever appropriate.

Avoid repeatedly sending complete annual reports to the AI.

Persist the following information:

Stock symbol, company name, financial year, report source, report version, download date, analysis date, processing status, AI model, token consumption and analytical output.

Provide an annual report dashboard showing:

- Total eligible stocks.
- Reports available.
- Reports processed.
- Reports pending.
- Failed reports.
- Daily batch progress.
- Token consumption.
- Last successful processing date.
- Next scheduled batch.

## 6. Additional architectural recommendations

I would add three specific controls to make this genuinely production-grade.

A. Golden master testing

Before consolidation, save each original screener's output for a fixed historical date and stock universe. Use it as the reference dataset for every future regression test.

B. Data download audit

Maintain a central download ledger:

| Ticker | Data type    | Date   | Source | Download count |
| ------ | ------------ | ------ | ------ | -------------- |
| TCS    | OHLCV        | 31-Oct | Yahoo  | 1              |
| TCS    | Fundamentals | 31-Oct | Yahoo  | 1              |
| INFY   | OHLCV        | 31-Oct | Yahoo  | 1              |

This makes duplicate downloads measurable rather than relying on assumptions.

C. Module isolation

A future enhancement analysis, management-quality analysis, dividend analysis or another screener should be addable without changing the existing three screeners.
